01 Executive Summary

The Student Hub is a new consumer-facing web application that serves as a courses and skills marketplace — a platform where students discover, purchase, and consume short-form upskilling courses (ranging from a few hours to a few weeks). Think of it as a purpose-built Udemy-style marketplace, tightly integrated with our existing Provider Marketing Hub where learning institutions already publish and manage their course catalogs.

While the Provider Marketing Hub serves hundreds to a few thousand institutional users and is built on React, TypeScript, GraphQL, and Supabase, the Student Hub must be architected for a fundamentally different scale: millions of concurrent student users. This difference in scale — along with different usage patterns (high-read catalog browsing, bursty purchase traffic, interactive content consumption) — justifies a purpose-built architecture rather than extending the existing provider-side stack.

Key Architectural Decisions

  • Separate system, shared course data — Student profiles, enrollments, progress, and transactions live in a dedicated database. Course catalog data is synced from the existing Supabase instance (read-only from the Student Hub's perspective).
  • Edge-first, SSR/SSG hybrid frontend — The catalog (the most-visited surface) is statically generated and served from the edge for sub-second load times worldwide. Personalized pages use server-side rendering.
  • Separate authentication system — Students authenticate through a dedicated auth provider, decoupled from the Supabase Auth used by providers.
  • Stripe-powered commerce — All financial transactions route through Stripe, keeping payment data off our servers entirely (PCI SAQ-A compliance).
  • English-first, i18n-ready — Launching in English with the architecture wired for future localization without rewrites.
Relationship to Provider Marketing Hub

The Student Hub is a consumer of course data published through the Provider Marketing Hub. Providers continue to manage courses, pricing, and content through their existing dashboard. The Student Hub reads this data via a synchronization layer — it never writes back to the provider-side Supabase instance.

02 Requirements Summary

2.1 Functional Requirements

The Student Hub's feature surface is intentionally focused on the core marketplace loop: discover → evaluate → purchase → consume → track. Each functional area below maps directly to this journey.

Feature Area Description Priority
Course Discovery Full-text search with typo tolerance, category/tag browsing, filtering by price, duration, skill level, and provider. Personalized recommendations based on enrollment history and browsing patterns. P0 — Launch
Course Detail Pages Rich course landing pages with syllabus, provider info, reviews/ratings, pricing, and a preview of content. These pages must be SEO-optimized and shareable (Open Graph / social cards). P0 — Launch
Student Accounts Registration (email + social OAuth), login, profile management, password reset, email verification. Students have a dashboard showing enrolled courses, progress, and purchase history. P0 — Launch
Purchasing & Checkout Single-course purchase via Stripe Checkout or Stripe Elements. Support for discount/promo codes. Purchase confirmation emails. Transaction history accessible from the student dashboard. P0 — Launch
Content Consumption In-app content player for text lessons, interactive exercises, quizzes, and code playgrounds. Linear and non-linear navigation through course modules. Auto-save of progress at the lesson level. P0 — Launch
Progress Tracking Per-lesson and per-course completion tracking. Visual progress indicators on the student dashboard and within the course player. Resume-where-you-left-off functionality. P0 — Launch
Certificates Auto-generated completion certificates (PDF) upon finishing all required modules in a course. Verifiable via a unique URL. Downloadable and shareable. P1 — Post-launch
Notifications Push notifications for: enrollment confirmations, course updates from providers, promotional offers, progress reminders. Delivered via in-app notification center and email. P1 — Post-launch
Reviews & Ratings Students can rate (1–5 stars) and review courses after enrollment. Aggregate ratings displayed on course detail pages. Moderation pipeline for flagging inappropriate content. P1 — Post-launch

2.2 Non-Functional Requirements

Requirement Specification Rationale
Performance LCP < 1.2s (P75), FID < 100ms, CLS < 0.1. JavaScript bundle < 150KB gzipped for initial load. API responses < 200ms (P95). Consumer-grade expectations. Slow catalog pages directly reduce conversion rates — every 100ms of latency costs ~1% in sales.
Scalability Horizontal scaling to 10M+ registered users, 100K+ concurrent sessions. Catalog browsing must scale independently of purchase/enrollment operations. Student user base grows orders of magnitude beyond the provider base. Read-heavy traffic (catalog) must not compete with write-heavy traffic (enrollments).
Availability 99.95% uptime SLA. Checkout flow: 99.99% (degraded mode acceptable elsewhere). Zero data loss on transactions. Payment failures erode trust immediately. A student who fails to purchase once may never return. Catalog can tolerate brief staleness; payments cannot.
Security PCI DSS SAQ-A (via Stripe — no card data touches our servers). OWASP Top 10 mitigations. HTTPS everywhere. Content Security Policy. Rate limiting on auth and payment endpoints. Input sanitization on all user-generated content. Financial transactions and student PII demand defense-in-depth. Delegating card handling to Stripe minimizes PCI scope dramatically.
Maintainability End-to-end TypeScript. Monorepo with shared types between frontend and API. Automated CI/CD with preview deployments. > 80% test coverage on critical paths (checkout, auth, enrollment). Type safety across the stack prevents an entire category of runtime bugs. Preview deploys accelerate review cycles. Coverage thresholds protect revenue paths.
Accessibility WCAG 2.1 AA compliance. Keyboard navigation, screen reader support, sufficient color contrast, focus management. Automated a11y testing in CI. Educational platforms serve diverse populations. Accessibility is both a legal requirement in many jurisdictions and the right thing to do for an education product.
Internationalization English-only at launch. Architecture must support: RTL layouts, locale-aware formatting (dates, currency), string externalization, and content translation — all without structural refactoring. Retrofitting i18n is expensive. Baking in the infrastructure now (even unused) is far cheaper than rewiring string handling, layouts, and formatting later.
SEO Course catalog and detail pages must be server-rendered or statically generated for full crawlability. Structured data (JSON-LD) for courses. Sitemap generation. Social sharing meta tags (Open Graph, Twitter Cards). Organic search is the primary acquisition channel for marketplace platforms. A course page that isn't indexed is a course that won't sell.

2.3 Constraints & Boundaries

Hard Constraints
  • Course data lives in Supabase — The Provider Marketing Hub stores all course metadata, content, and pricing in a Supabase PostgreSQL instance. The Student Hub must read from this source of truth. It cannot modify provider-side data.
  • Student data must NOT live in Supabase — Student profiles, enrollments, progress, and transaction records must be stored in a separate database system, fully decoupled from the provider-side infrastructure.
  • Separate auth system — Students authenticate via a dedicated identity provider, not the Supabase Auth used by providers. There is no SSO requirement between the two systems.
  • Web-only — No native mobile application. The web app must be fully responsive and performant on mobile browsers, but native apps are out of scope.
  • Stripe for payments — All payment processing routes through Stripe. No alternative payment gateways at launch.

Design Principle: Anonymous-First

The most critical pages in the funnel — discovery and evaluation — are consumed by anonymous users. These pages must be the fastest, most cacheable, and most SEO-friendly. Authentication is only required at the point of purchase. This directly influences our rendering strategy: static generation for the top of the funnel, server rendering for the authenticated bottom.
